# Исследование Digiseller API для 1.0.4

Официальная документация: https://my.digiseller.com/inside/api_catgoods.asp и https://api.digiseller.com/swagger/ui/index

## Подтверждено документацией
- `GET /api/categories?seller_id={seller_id}` выдаёт дерево категорий **конкретного продавца**.
- `GET /api/shop/products?seller_id={seller_id}&category_id={category_id}` выдаёт товары категории **конкретного продавца**.
- `GET /api/products/{product_id}/data` возвращает `product.category_id` и `product.breadcrumbs` **при передаче seller_id** (в текущем запросе приложения seller_id отсутствует).
- Описанные в API поля `collection` и `type` означают тип содержимого/доставки, **не** тип Steam Gift или Steam Key.

## Не подтверждено
- Параметр категории в глобальном `GET /api/products/search2` для фильтрации Gift/Key. Нельзя добавлять `category_id` к `search2` без проверки его фактической поддержки.
- Единая глобальная классификация всех продавцов на Gift/Key/аккаунты: seller category ID может быть уникальным для магазина.

## Вывод для реализации
Не следует выдавать категории продавца за общую классификацию Steam. Без надёжного определения продавца и семантики категории серверный фильтр может удалить корректные предложения. Следующий этап — исследовать структуру реальных ответов `search2`, определить seller_id и проверить применимость category breadcrumbs для нескольких продавцов. До этого сохранить клиентский фильтр и не утверждать, что серверная фильтрация реализована.

## Дополнение: категории торговых площадок (19.10.2026)

В Swagger Digiseller обнаружена **отдельная классификация площадок**, отличная от дерева категорий магазина:

- `GET /api/dictionary/platforms/subcategories/{category_id}` — справочник подкатегорий площадки.
- Модель `ProductCategory` включает `owner`: `0` — магазин продавца, `1` — Plati, `2` — WMCENTRE, `3` — GGSEL; а также `category_id`, `cataloguer_category_id`.
- Это перспективнее для фильтрации Plati, чем произвольные категории отдельных продавцов. Но связь полей с **публичным** ответом `search2` и значения для Gift/Key/аккаунтов ещё не проверены. Нельзя считать эти категории реализованным фильтром.

Документация: https://api.digiseller.com/swagger/ui/index ; https://api.digiseller.com/Help/Api/GET-api-dictionary-platforms-subcategories-category_id

## Следующий безопасный шаг
Получить реальные ответы `search2` и `/api/products/{id}/data` для нескольких товаров каждого типа, сопоставить категории площадки с проверенными карточками, затем вводить фильтр с запасным вариантом при отсутствии категории. Не удалять предложения только по неизвестному числовому ID.

## Реальная проверка API в CI (19.10.2026)

Добавлены `scripts/probe_digiseller_categories.py` и `.github/workflows/digiseller-categories.yml`. GitHub Actions автоматически запускает отдельную **исследовательскую** задачу при изменении этих файлов (или вручную через `workflow_dispatch`). Артефакт `digiseller-category-probe` содержит JSON с деревом категорий Plati и именами полей категорий из нескольких запросов `search2`, **без названий и ID товаров или продавцов**.

**Важное уточнение документации:** `GET /api/dictionary/platforms/categories/{id}` принимает **строковый код площадки** `plati`, `wmcentre` или `ggsel`, а не число `1`. Значение `owner=1` относится к другой модели — владельцу категории товара/параметру поиска. Это разные идентификаторы.

`search2` официально перечисляет параметры `pagesize`, `pagenum`, `owner`, `sortmode`, `searchmode`, `query`, `details`, `ids`, `ids_shop`, `idr`, `rkn_filter`, `pp_only`, `host`, `lang`, `checkhidesales`, `token`; отдельный `category_id` среди документированных параметров не указан. **Это не доказывает невозможность фильтрации через другие публичные API**, но исключает предположение, что `category_id` документирован для `search2`.

Следующий этап: получить и изучить артефакт исследовательской задачи, сопоставить названия категорий с типами Gift/Key/аккаунт и определить доступность связей категорий в публичных карточках товаров. Пока функциональная фильтрация по категориям в Android-приложении **не реализована**.

Источники: https://api.digiseller.com/Help/Api/GET-api-dictionary-platforms-categories-id ; https://api.digiseller.com/Help/Api/GET-api-dictionary-platforms-subcategories-category_id ; https://api.digiseller.com/

## Исследование связи категорий и карточек (коммит beae414)
- Проба расширена: проверяет до 40 корневых категорий Plati и до восьми публичных карточек из реального `search2`. ID товаров используются только в оперативной памяти скрипта, в отчёт не сохраняются.
- В отчёте появились `search.*.sample_category_metadata` и `product_details[].category_metadata` / `category_field_names`: позволяют установить, присутствуют ли `category_id`, `breadcrumbs`, `subcategory_id` или `owner` у реальных товаров.
- **Результат GitHub Actions пока не удалось получить:** доступный GitHub-коннектор возвращает пустой список запусков по коммиту (его метод учитывает только PR-triggered runs), а для чтения артефактов нужен run ID. Поэтому реальные категории и их соответствие Gift/Key/аккаунтам **пока не подтверждены**. Не вводить произвольные ID категорий в Android-код.
- Внешний доступ к api.digiseller.com из текущей рабочей среды не разрешился по DNS; это не свидетельствует о недоступности API в GitHub Actions.
- Следующее действие: открыть https://github.com/Magral/Igrolov/actions/workflows/digiseller-categories.yml , получить `digiseller-category-probe` и изучить значения категорий и наличие связей в карточках. После этого реализовать обоснованную фильтрацию.

## Подтверждённый результат CI #1 — полученный JSON-артефакт

Исходный артефакт `digiseller-category-probe.zip` получен от пользователя и прочитан 19.10.2026. Это отчёт **первого** workflow, до расширения проверки карточек товаров.

- `GET /api/dictionary/platforms/categories/plati`: `retval=0`, четыре категории: `1` Электронные книги, `2` Программное обеспечение, `10` Ключи и пин-коды, `138` Цифровые товары; у всех `parent_id=519`.
- Для всех четырёх запросов `/api/dictionary/platforms/subcategories/{id}` исследовательский скрипт записал `count=0`. **Это не доказывает отсутствия подкатегорий:** вспомогательный парсер `rows()` мог не распознать структуру ответа.
- `search2` с `Hogwarts Legacy Steam` и `Cyberpunk 2077 Steam`: по 30 товаров; в обоих ответах нет полей с `categor`. Есть `owner_id`, `owner_name`, `seller_id`, `seller_name`, `seller_rating`.
- **Не обнаружено прямой связи** `search2` с категориями. Нельзя фильтровать глобальную выдачу по `category_id=10` без отдельного подтверждения поддержки параметра и соответствия конкретного товара категории.
- Отчёт расширенного workflow с `product_details` ещё не получен. До него серверную категоризацию Gift/Key/аккаунт считать нерешённой.

## Подтверждённый расширенный отчёт CI #2 — связь категорий с карточками

Получен второй пользовательский артефакт `digiseller-category-probe (1).zip`, содержащий JSON расширенного workflow (19.10.2026).

- Дерево площадки: те же четыре категории Plati (`1`, `2`, `10`, `138`), `retval=0`.
- `search2`: по 30 товаров для `Hogwarts Legacy Steam` и `Cyberpunk 2077 Steam`; ни у одного из 60 товаров нет поля категории. Поля продавца и владельца присутствуют.
- **Восемь реальных карточек** `/api/products/{id}/data`: во всех `retval=0`, `product.category_id=0`, `product.breadcrumbs=[]`, `product.owner=1`.
- `errors=[]`: скрипт не зафиксировал ошибок HTTP/JSON. Но `rows()` по-прежнему сообщает 0 подкатегорий; это может быть ограничением парсера, а не API.

**Решение:** нельзя приписывать товарам из `search2` категорию `10` или любую другую категорию справочника. Нет подтверждённой связи категории с товаром в проверенных ответах. Серверный фильтр `category_id` для `search2` не документирован. Не внедрять неподтверждённую категоризацию: Gift/Key/аккаунт пока различаются клиентскими правилами заголовка, а неизвестные типы исключаются из автоматических уведомлений. Исследовать документированные альтернативные endpoints, включая seller-specific API, отдельно.

## Seller-specific проверка: реализация (коммит af7410e)

Исследовательский скрипт теперь извлекает до трёх различных `seller_id` из реального `search2` и для каждого продавца выполняет:

1. `GET /api/categories?seller_id=...` — проверяет дерево категорий конкретного магазина.
2. `GET /api/products/{id}/data?seller_id=...&currency=RUB&lang=ru-RU` — проверяет, появляется ли `category_id` и непустой `breadcrumbs` при передаче продавца.

В `digiseller_category_probe.json` добавляется `seller_samples`: только номер анонимной выборки, количество и названия категорий, наличие ненулевого ID категории и количество breadcrumbs. ID продавцов/товаров не сохраняются. Важно: категория конкретного магазина не является автоматически Steam Gift/Key; даже при ненулевом ID нужно проверить семантику названий и принадлежность конкретного товара.

**Результаты новых запросов пока не получены.** GitHub Actions автоматически запускается при изменении скрипта. Не утверждать, что связь категорий доказана, пока нет артефакта этого запуска.

## Подтверждённый seller-specific отчёт CI #3 (19.10.2026)

Из загруженного пользователем `digiseller-category-probe (2).zip`:
- Для трёх различных продавцов запрос `GET /api/categories?seller_id=...` дал `retval=0`, но текущий парсер `rows()` нашёл `count=0` для всех. Пока нельзя отличить пустые категории от неизвестной формы JSON-обёртки.
- `GET /api/products/{id}/data?seller_id=...`: **у одного из трёх** товаров появился ненулевой `category_id` и один элемент `breadcrumbs`; у двух других — `category_id=0`, `breadcrumbs=[]`. Все три ответа `retval=0`.
- Это **реально подтверждает**, что `seller_id` иногда раскрывает категорию товара, но не подтверждает общую таксономию Gift/Key/аккаунт и не даёт права исключать товары с пустой категорией.

Коммит `ca1899f`: улучшен разбор вложенных ответов и добавлена обезличенная структура JSON (`response_structure`) для категорий продавца и подкатегорий Plati. Новый workflow должен показать, почему прежний парсер возвращал ноль. Идентификаторы товаров и продавцов не сохраняются в отчёт.

## Подтверждённый seller-specific отчёт CI #4 — названия категорий (19.10.2026)

Артефакт `digiseller-category-probe (3).zip` изучен непосредственно. Обновлённый парсер корректно извлёк массив `category` из `GET /api/categories?seller_id=...`:
- Продавец №1: **6** категорий, в том числе «Стим Ключи»; его проверенная карточка имеет ненулевой `category_id` и один breadcrumb.
- Продавец №2: **3** категории, включая «ПОПОЛНИТЬ STEAM», «ПОВЫСИТЬ УРОВЕНЬ STEAM», «ОЧКИ STEAM»; проверенная карточка имеет `category_id=0`.
- Продавец №3: **16** категорий, включая «Steam», «Steam Gifts», «Игры»; проверенная карточка имеет `category_id=0`.
- Все три `GET /api/categories` вернули `retval=0`. Пробный `search2` по-прежнему не содержит полей категории в 60 товарах.
- Запросы подкатегорий площадки возвращали JSON с `errors` и `content=null`, поэтому прежнее `count=0` **не означает** пустой справочник. Нужно фиксировать `retval` и коды ошибок отдельно.

**Реальный вывод:** семантически полезные категории Steam Gift/Key существуют в **каталогах отдельных продавцов**. Однако нельзя считать ID таких категорий универсальными, а категория «Steam» сама по себе не определяет способ доставки. Для безопасной фильтрации требуется установить точное соответствие `(seller_id, product.category_id)` ↔ название категории, с осторожной обработкой `category_id=0` и неоднозначных названий.
